## Authorization Boundary

Work §5.1 task-wide duties apply to this Human instruction from entry, including read-only admission
and Run preparation. Carry completed outcome-based preparation progress and due drift checks into
each governing Run; the Domain/Initialization boundary does not reset the same task's consumption.

The Human initialization command authorizes two bounded Runs: first Domain Foundation preparation
and its Human Domain Decision, then Bootstrap Initialization and its Human Initialization Gate. It
does not approve either Gate or authorize a functional prototype or delivery-intended Product work.

Read/assess/explain-only requests authorize only the answer and minimal inspection: no Run,
Foundation or initialization output. An explicitly Domain-only task stops at the Domain Gate;
100% names that bounded output/handoff, not an effective Foundation or whole Initialization.

## Phase A — Domain Foundation

1. **Read-only admission:** verify manifest/trust anchor, Bootstrap State, exact Human instruction,
   Git/tools/Agent capability, and named inputs. Classify secrets, PII, confidentiality, and rights;
   hash safe bytes in place without copying, executing, or modifying inputs.
2. **Run preparation:** use the active Bootstrap Work Contract as scope. Prepare a
   `domain_foundation` Run whose targets are only pre-existing Human, Bootstrap, and input sources;
   the Foundation, review pack, and decision are outputs. Before substantive preparation obtain
   the exact preparation Spawn pass; before implementation obtain the separate Run-bound pass.
   Persist actual clearance, run `--check-run`, coordinate actual conflicting writes under Work §5.2 and set `active` before outputs.
3. **Agent-start and perspectives:** Domain Foundation is D3. Under1.4.0+, two working Agents plus
   separate temporary Spawn are the default; older pins retain their limits. Clear each actual
   responsibility before it starts; do not pre-clear a future reviewer. Product, UX, Architecture, Quality and
   Devil/Simplicity functions cover language/outcome, boundary cohesion, feasibility, and
   overcomplication; no new permanent role or extra headcount is created.
4. **Bounded model:** from confirmed evidence, distinguish provisional actors/use cases from
   decisions. In the existing Foundation reference sufficient C1–C3 sources and name only actual
   gaps/conflicts needing modeling or consolidation; do not rewrite inputs to fill a template.
   Model the MVP and first-six-week horizons: Bounded Contexts and responsibilities,
   Context Map relationships, Ubiquitous Language, structural elements and cardinalities,
   behavior/state/invariants, roles/permissions, First-Class Product Objects, negative boundaries,
   and one logical module per Context with pragmatic hexagonal projection. Detailed IA, routes,
   screens, contracts, provider design, delivery slices, and implementation remain prohibited.
5. **Review and Human Domain Decision:** independently review the exact digest-bound candidate;
   consolidate only evidence-backed findings, close blockers, and record dissent. Assemble the
   Foundation review pack, set the Run to `verification`, update handover and
   stop. Explain adopted knowledge, new learning, real decisions/alternatives, Product consequences
   and recommendation/uncertainty first; put technical bindings in detail. If no open modeling
   choice remains, say so and request exact Foundation approval without invented options.
   Pending Human decision and an ineffective Foundation are valid at this verification stop.
   Only the Human may approve the exact revision as `domain_model_effective`; recheck on resume.

## Phase B — Bootstrap Initialization

6. **Separate Run:** after an effective Human Domain Decision, create a
   `bootstrap_initialization` Run targeting the exact Foundation/decision and active Bootstrap
   contract. Complete Preflight, Agent-start, direct check and activation independently;
   do not recreate or silently reinterpret the Foundation.
7. **Independent understanding:** Product, UX, and Architecture perspectives restate why, target
   users, core outcome, evidence, uncertainty, risks, and counterevidence against the Foundation.
   These are lenses, not a document or Agent per function. The version-appropriate team and bounded
   dissent escalation follow Collaboration; no Agent approves its own material artifact.
8. **Product foundation:** create the Product/Vision Brief, detailed requirement dispositions,
   actors/use cases/journeys, MVP/non-goals/success/kill conditions, and 3/6/12-month hypotheses.
   Record privileged Product access as `applicable | not_applicable | unresolved` and keep its
   Product behavior in Product/domain/contract owners.
9. **Technical and release foundation:** bind Harness/profile versions; create Product Technical
   Delta, Product Release Policy, Domain/Contract/Orchestration Target Specs, ADRs, and
   security/data/cost posture. Use SemVer by default unless evidence supports a fully deterministic
   alternative. Map every Context to one logical module; create ports/adapters only for real
   boundaries and keep framework/persistence dependencies outside domain cores.
10. **Design contract before creation:** classify visual sources and create a compact Mockup
    Contract with digests, coverage, identity axes, allowed deltas, bounded surfaces/states,
    maintained source/render evidence, budget, and stop. UI structure follows user tasks across
    Contexts; it does not mirror Contexts, aggregates, or Product Objects one-to-one.
    Before costly rendering, the assigned reviewer walks the existing Design §7 meaning: user
    work-object, distinct statuses, guarded actions, decision scope/invalidation, partial progress,
    change/recheck/final outcome and downstream boundary. Reuse valid sources and bounded deltas.
    This early lens consumes the existing review budget, not an additional full review or Gate.
11. **Adaptive design reference:** create the smallest coherent Design System v0 and
    `design_reference_only` Interactive HTML Mockup needed for the primary outcome. Preserve
    adequate supplied sources, fill only real coverage gaps, use deterministic renders, and never
    connect Product backend/cloud/provider/secrets.
12. **Rolling plan:** create Milestone, three two-week checkpoints/six-week horizon, capability
    mapping, vertical Delivery Slices, modular Work Packages, deployment policy, and proposed Runs.
    Each changed Context binds the effective Foundation revision. The first Slice is a real-value
    Walking Skeleton; a prototype is either that Slice or a non-promotable risk experiment.
13. **Independent review:** reviewers confirm Product Vision and Foundation consistency, then
    inspect exact baseline/candidate sources, matched renders, flow traceability, plan, architecture,
    cost, risks, and user outcome. Close all blocks without reopening the Domain Decision.
14. **Review Pack and Gate:** update Product orientation; assemble exact digests, decisions,
    dissent, assumptions, evidence, and separate requested approvals. Set the Run to
    `verification`, update handover and stop at the Human Initialization Gate.
    Foreground the actual decisions and consequences in Product language; preserve separate Gate
    authority and retain valid Domain evidence rather than reviewing it all again.
15. **Resolve decision:** for unchanged scope, re-check the Contract, coordinate actual conflicting writes, and set
    it `active`. After authorized correction or approval, update evidence/handover, set it
    `completed` and leave delivery Runs separately approved.

## Mandatory Stop Output

- effective Domain Foundation revision and Human Domain Decision;
- one-page “what we believe and why” plus Product/Vision and requirement disposition;
- linked Review Pack, Mockup Contract, runnable design reference, and matched storyboard where UI applies;
- unresolved decisions with recommendations and exact approvals requested;
- first Delivery Slice/Walking Skeleton and proposed Run IDs, not automatically active;
- privileged Product-access disposition and exact protected-reference plan when applicable;
- exact Product Release Policy/version recommendation;
- explicit statement that Product implementation has not begun.
