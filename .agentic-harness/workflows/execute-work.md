## Routine First

Optional Harness logging is off by default. Only explicit task activation uses
[the logging workflow](harness-logging.md); reuse existing observations and create no extra Run.

After mandatory entry/integrity and narrow task context, classify impact, reversibility and actual
uncertainty under Collaboration §4. For1.5 D0 prescribed low-risk copy/appearance, use task → diff →
focused result check. Reuse existing flow/Use Case; do not model a new flow for a title correction.
No Run/WP/Slice/Domain Binding/Spawn/review/percentage form, and no automatic new tests. Exclude
price, rights, data, contracts, interactions, material UI and unknown impact. Finite work bound and
one correction apply. Stop when requested result is proven.

If delivery is authorized by this task or approved Product policy, use Delivery §2.2's routine RC
variant and exact outcome evidence through Staging. Existing relevant build/security checks,
version reservation and Production Gate remain. Local edit permission alone
is not deploy authority. An unadapted Product workflow is a narrow explicit limitation, never a
reason to forge Work objects. The steps below are the material path.

## Start

Work §5.1 applies from receipt of this task, including every Start/Preflight step below. Carry actual
preparation progress, due checks and cumulative budgets into the Run's existing progress section;
never initialize them again at `active`. Before each mutation stretch, review, external action,
completion or resume, assess changed duty applicability. Reuse unchanged evidence and Contract
checks; invoke `--check-run` at start/resume and when its actual inputs change under Admission §4,
not for every in-scope edit or prose update. The Lead maintains the one aggregate progress/drift
sequence; delegated substeps and sample subjects report results/open work without their own
percentage ladder or40/80% review holds.

1. Read mandatory entry chain, Product Vision Brief and applicable Domain §12 sources: exact
   Foundation/context coverage for affected Contexts, or the existing scope/context decision
   supporting a wholly domain-free Package's explicit `not_applicable_reason` under1.4.1+.
2. Verify Run kind/class/trigger, Slice and ordered Packages, outcome/completion evidence, deployment
   and external authority, assignments, finite cumulative/concurrent review/correction budgets,
   escalation and stop. Bind the Scope Lock: minimum outcome/change, allowed paths, prohibited
   outcomes, follow-up-only adjacency and amendment before expansion. D1–D3 use two working
   Agents plus separate temporary Spawn (three identities). Distinguish original outcome, actual
   source observations and action permission; resolve consequential contradictions first. Older pins

   binds its envelope, current Package/digest, remaining total and non-Human Package Authority.
3. For D1-D3, have the Spawn Reviewer clear the Agent actually starting and record the pass directly

   Follow the repository branch policy.

A material Run binds its approved design reference or the predeclared authority's standalone-review decision plus representative critical surfaces before first UI mutation; a minor Run binds that authority's direct rationale. ## Plan And Review

- Keep one durable material-work plan in the existing Work/Run progress section, or reference the
  existing Human-supplied plan. Map original requirements and subsequent authorized changes to
  required results, open/verified state, evidence and next step. Update changed items at work
  boundaries and before pause; link this owner from existing handover. Do not add a second list.
  Review original source coverage before the proposed approach; preserve unresolved requirements.

- Confirm the Slice's observable user/operator outcome, acceptance/anti-criteria, non-goals, connected flow, Package boundaries, do-not-touch paths, domain/contracts, approved UI/design-reference revision, its binding covered surfaces, existing Product-wide UI owners, migrations, tests, Staging/user evidence, release-candidate identity, cost, and recovery. General Product/UI improvement authority does not permit reinterpretation of a supplied mockup; redesign requires an exact Package outcome.
- Confirm each changed Context binds the exact effective Foundation revision or an approved
  context-specific Brownfield legacy exception. Do not infer permission from unrelated modeled
  Contexts and do not require migration of untouched legacy areas.
- For the Domain §12 domain-free variant, verify its reason against the exact sources and whole
  Package scope. Unknown or emerging domain impact requires resolution/binding before affected
  mutation. This variant does not waive design, authority, review or parent-Slice evidence.
- Apply the evidence-led simplicity test: start from the known problem and current evidence; choose the simplest sufficient approach; map every non-obvious mechanism to a confirmed requirement, observed problem, or concretely applicable higher obligation; defer hypothetical, generic, and extreme-edge work with a concrete trigger.
- Obtain Package reviews and the independent Product/User, Architecture/Engineering, and Approval/Simplicity Slice review required by decision class.
- Before expensive material workflow-UI creation, the assigned reviewer walks Design §7's existing
  source-bound meaning: work-object/grouping, lifecycle versus revision/progress/final decision,
  screens/actions/guards/effects, decision validity and change/recheck/completion/downstream path.
  A valid existing flow plus bounded delta suffices; no new universal flow document or full review.
- Required lenses may share the independent reviewer, not the creator. After one clarification,
  a critical competence gap or unresolved material dissent follows the bounded third-working-Agent
  allocation; Spawn has no content vote. A2/3 tradeoff decision cannot erase an evidenced blocker,
  change final-approval authority or waive a Human Gate. No infinite consensus/correction loop.
- Reviewers challenge the creator's exact revision; they do not build parallel solutions. Classify findings `in_scope_blocking | in_scope_non_blocking | adjacent_follow_up`. Collect all findings before one consolidated correction. Closure review stays on affected findings unless the correction creates a concrete regression. Beneficial but unauthorized changes remain follow-ups and never become blocking implementation scope.
- A reviewer brief must route the exact artifact/candidate revision and required evidence rather than only an implementer's summary. Missing evidence is `not_observed`; the reviewer requests it and cannot return PASS.
- If a Package or Slice is too large or too small, stop affected mutation; propose a D2 split/merge preserving outcome, flow, contracts, dependencies, deployment/rollback boundary, order, and Milestone outcome.

## Implement And Verify

1. Before selecting a Mission Package and before its first mutation, bind one compact intent: named Mission outcome, exact Package revision, behavior, permitted semantic owners/paths/environments/actions, invariants/non-goals, criteria, remaining budgets, and reversible assumptions. For1.5.1+ retain it in the existing Work/Run plan before mutation and reference the exact section/revision at checkpoint; no parallel intent hash. Historical Mission pins retain their fields.
2. Implement each Package only against the exact approved Target Spec revisions named by it and map every changed path to a required Scope-Lock and, where present, Mission outcome; they remain `approved target`, not current system truth, during implementation. Repeat the intent check before expanding a path, owner, environment, or action.
3. Implement through owned domain/application/port/adapter boundaries. Technically reimplement each binding mockup surface without changing its covered observable contract. In an existing Product reuse its established shared shell, approved UI components and global tokens; a local screen must not fork or silently change those Product-wide owners.
4. Run the smallest relevant existing checks before expensive deployment, using the same commands
   locally and in CI. Include actual changed helpers/configuration/permission dependencies. Reuse
   unaffected evidence/builds; do not run arbitrary transitive suites. Mocks do not prove IAM.
5. Start locally where applicable and inspect behavior, not only exit codes.
6. After implementation and before review/integration, independently re-check the actual changed paths, behaviors, and non-obvious mechanisms against Package and Mission outcomes, permitted owners/paths/environments/actions, invariants/non-goals, current evidence, assumptions, and remaining budget. Remove unmapped changes, speculative abstraction, generic optionality, and untriggered extreme-edge handling or stop; do not defer this check to continuation.
7. Continue the Work §5.1 progress/drift cadence already begun at task entry. A missed duty blocks
   affected continuation until honestly disclosed and resolved; no fabricated earlier report/check.
8. Commit/push coherent Package checkpoints when authorized. Close Package findings and move exact integrated revisions only to `slice_ready`; do not claim Staging or technical acceptance and do not deploy each Package by default.
9. If a predeclared IAM/CDK, migration, auth, provider, central-contract, uncertainty, or blast-radius trigger is met, create at most the authorized bounded `verification_candidate`, bind Product version/tag/Policy as `not_applicable`, deploy to the authorized isolated/shared environment, capture its hypothesis evidence, clean/restore state, and retain `non_promotable` status. Otherwise continue locally.
10. When all Packages are `slice_ready`, build application/migrations once, produce both environment-specific CDK assemblies/diffs, and completely render/freeze the final Product Delivery Release Candidate Manifest bytes in transaction staging. Use the approved Product Release Policy to bind their `reserved_unpublished` intended Product version/tag/Policy identity and compute the exact RC digest. Check release-identity collisions and atomically persist the frozen candidate and identity event under Product Release Versioning. A corrected RC retains the version only through the existing atomic same-scope reservation transfer; otherwise select another version.
11. Deploy that exact final candidate to Staging; exercise the complete connected Slice outcome with isolated personas/fixtures and capture screenshots, logs, resources, security, provider, and cost evidence. Where privileged access applies, verify separate synthetic normal/Admin/automation identities, server-side denial and tenant boundaries, activation/reset, expiry/revocation, and recovery without any Production principal or credential.
12. Review as a critical but fair target user against Vision, correctness, usefulness, flow, usability, UI/UX, accessibility, trust, latency, failure/recovery, and the approved design reference. For `material_ui`, retain a few predeclared representative candidate images and, when a mockup exists, baseline images, all bound to the exact candidate in the existing Run evidence directory; validate the actual raster bytes and digests. The Product/UX reviewer must inspect every named image through a browser or image tool and bind those IDs in the existing Review record. Without a mockup, use the preauthorized standalone critical-user path rather than inventing a baseline. Missing access is `not_observed` and blocks; screenshot presence alone is not approval. There is no finding quota.
13. Disposition every Package/Slice finding; originating reviewers verify closure. A defect introduced by a correction remains eligible while the same user outcome, Scope Lock, risk boundary and finite Run/Mission authority remain. From current evidence the Lead may `correct`, `simplify`, `rollback`, or `reimplement`, recording expected user benefit and the validation/rollback trigger in the existing checkpoint. Confirm `critical` only through the class quorum and keep one causal-chain ID across agents/Runs. Each same-chain remediation uses a distinct hypothesis. Critical recurrence triggers a proportionality/convergence decision, without a separate numeric
    ceiling; Work §10 owns the single reserve and two-failed-diagnostics decision. Other legitimate findings continue within scope and cumulative budget. Open blocks prevent acceptance.
14. On ordinary resume or correction, re-check the same Contract. Correction
    re-entry stops at the declared ceiling and a non-Mission Run cannot draw Mission reserve. A
    material scope, authority, action, target or budget change increments the Contract revision and
    records its reason and Decision Authority there; Git preserves the predecessor. An exceptional
    Human budget amendment changes only that Contract and never creates reviewer capacity by itself.
15. Before closing, the independent reviewer walks every original requirement and authorized change
    in the existing plan against actual implementation/evidence; missing required work remains open.
    A plan reduction needs the owning Human decision, not a renamed follow-up. The non-author
    Slice Final Approver accepts or rejects the exact final candidate/Evidence revision. Finalize the existing immutable Review Record only after evidence/closure; bind candidate,
    verified spec revisions and predecessors, authority and actual result. Deployment history → RC
    → Review is discoverable without chat. Work/navigation is derived; no spec move or mandatory
    post-delivery metadata commit. An explicit notification failure remains unresolved task work
    and resumes only that safe step, never rebuild/deploy solely for archive/notification.
16. At every Mission Package boundary, checkpoint the readable intent reference (pre1.5.1: digest), actual Package-and-Mission path mapping, current evidence/invariants, assumptions/triggers/fallbacks, findings/follow-ups, attempts/budget, dependency drift, next item, and `continue | stop | escalate | complete` decision. Continue only when every guard passes; ordinary in-scope defects use the bounded correction loop without a Human gate.
17. Perform post-Slice Product/UX/Architecture/Quality revalidation, update the implementation-ready two-week and structured six-week plan, then checkpoint/handover and stop only at the authorized
    boundary. Continue a named next Slice after baseline/authority checks without a new Human gate.

## Stop Instead Of Guessing

Stop for integrity mismatch, missing authority/capability/secret/decision, unsafe side effect, unreviewed scope growth, material spec drift, exhausted Agent/review/correction budget, an unapproved escalation, or required Human Gate.

Completed historical start omissions use only the honest Human-authorized disposition in
Collaboration §1.2 / Ordinary Admission §6.1. It preserves valid old work but is never a start pass
or continuation authority; all new work retains timely separate Spawn Review.
